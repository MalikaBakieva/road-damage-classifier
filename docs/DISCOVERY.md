# Data & Problem Discovery

> Brief §5 — completed **before** implementation, as required.

| Decision / Question | Response |
|---|---|
| **Selected dataset and source** | **RDD2022 — Road Damage Dataset 2022** (Arya, Maeda, Sekimoto et al.). ~47,000 road images with 55,000+ PASCAL-VOC bounding-box annotations, collected from vehicle-mounted cameras across six countries. Public, permissively licensed (CC BY-SA 4.0), and the de-facto benchmark for this task, so results are comparable to published work. We use the **Japan, India and Norway** subsets: Japan gives volume and label quality, India adds unpaved/degraded surfaces, Norway adds northern lighting and winter conditions. Source: <https://github.com/sekilab/RoadDamageDetector>. See `docs/DATASET.md`. |
| **What does one record / sample represent?** | RDD2022 ships one *image* per record with zero or more damage boxes. We reformulate to one **image patch** per record: each annotated bounding box expanded by 25 % context becomes a labelled crop, and annotation-free road regions become `not_damaged` crops. Rationale: a single photo often contains several damage types, so a whole-image multiclass label would be ambiguous and unlearnable; a crop has exactly one defensible label. Some 480×480 images yield 1–4 samples. |
| **Proposed target or ML objective** | Two supervised classification heads, trained separately from the same crops. **Primary — binary:** `damaged` vs `not_damaged`. **Secondary — multiclass (5):** `not_damaged`, `longitudinal_crack` (D00/D01), `transverse_crack` (D10/D11), `alligator_crack` (D20), `pothole` (D40). The binary head answers the department's actual decision ("does this report need an inspection?"); the multiclass head adds routing detail where it is reliable enough. Codes D43/D44/D50 (crosswalk blur, white-line blur, utility hole) are **not** damage and are excluded from the damage classes. |
| **Key information available at prediction / inference time** | Only the **image pixels**. Nothing else is guaranteed: a citizen submission may have no GPS, no timestamp and no camera metadata. Any feature not present at inference is therefore excluded from training — this is the single hardest constraint on the design. RDD2022 offers country labels, but using them would create a feature the department cannot supply for a new photo. |
| **Main data quality issues** | 1. **Severe class imbalance** — longitudinal cracks dominate; potholes are roughly 8–10× rarer. 2. **Annotation inconsistency across countries** — the same crack can be boxed differently, or missed, by different annotators; India's labels are noticeably noisier than Japan's. 3. **Missed damage in "negative" regions** — an unannotated patch is not guaranteed to be undamaged, so some `not_damaged` labels are wrong (label noise that caps achievable recall). 4. **Variable image quality** — motion blur, low sun, wet reflections, shadows, compression artefacts. 5. **Tiny boxes** — some annotations are only a few pixels wide and carry no signal after resizing; we drop boxes below 24 px. 6. A handful of truncated JPEGs and malformed XML files, which the parser skips with a warning rather than crashing. |
| **Potential leakage risks** | 1. **Same-image leakage (primary risk).** Multiple crops come from one photo and share camera, lighting, road surface and often the same physical defect. Splitting at crop level would put near-duplicates in both train and test and materially inflate scores. **Mitigation:** all splitting is done at *image* level, and `tests/test_data.py::test_no_image_leaks_across_splits` fails the build if this is ever violated. 2. **Consecutive-frame leakage.** RDD2022 frames come from continuous drives, so adjacent images can show the same defect from a slightly different distance. Sequential filename IDs make near-duplicate frames likely neighbours; the residual risk is documented rather than claimed solved. 3. **Country-as-shortcut.** Country-specific road texture could let the model identify origin rather than damage; we never feed country as a feature, and per-country metrics are reported to detect it. 4. **Test-set peeking.** Model selection uses validation macro-F1 only; the test split is read exactly once, by `rdc.evaluate`. |
| **Privacy / fairness / licensing concerns** | **Licensing:** RDD2022 is CC BY-SA 4.0 — free to use with attribution; the citation is in `docs/DATASET.md`. **Privacy:** street-level imagery can contain readable licence plates, pedestrians and building frontages. The dataset is already public and we do not redistribute it (`data/` is git-ignored); a production deployment would need face/plate blurring and a retention policy, and citizen-submitted photos would be personal data under GDPR-style regimes. **Fairness:** the geographic mix is Japan/India/Norway, so performance skews toward those road-construction styles, weather patterns and camera setups. Applied to a city with different asphalt, markings or climate, error rates will differ — plausibly worse for lower-income neighbourhoods if their surfaces are less similar to the training distribution. Because the output drives *inspection priority*, systematic under-detection in one area means slower repairs there. Mitigation: report per-country and per-class metrics, keep a human-review path for low-confidence cases, and re-validate on local imagery before any deployment. |
